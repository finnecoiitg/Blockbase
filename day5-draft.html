Day 5

ERC-20 Tokens

Before you write a single line of token code, it's worth stripping away the mystique. Tokens — USDC, LINK, UNI, every ERC-20 you've ever seen in a wallet — are not a special kind of blockchain object. They are smart contracts. Contracts with a mapping from addresses to balances, a function that moves numbers between entries in that mapping, and a handful of utility functions that frontends use to display information. That's all there is to it.

What you built in Day 4 already contains the core of a token. The Balances contract had a mapping(address => uint) and a function that added to it. Extend that with a transfer function, a total supply tracker, and some standard naming, and you have a token. The ERC-20 standard is just the industry's agreement on what those functions should be called, so that every wallet, exchange, and dApp can interact with any token without writing custom code for each one.

The interoperability problem

Imagine if every bank used a completely different protocol for wire transfers. Bank A sends money one way, Bank B handles it differently, and no two are compatible. Every time you wanted to move money between banks, someone would have to write a custom integration. That's the situation Ethereum tokens were heading toward in 2015, when developers were building token contracts with different function names and signatures.

Fabian Vogelsteller and Vitalik Buterin proposed ERC-20 to fix this. ERC stands for Ethereum Request for Comment — a process borrowed from the early internet, where proposed standards are published for community review before becoming official. ERC-20 defined a minimum interface every token contract must implement. If your contract has these six functions and two events, any MetaMask-connected wallet can display your token balance, any decentralised exchange can list it for trading, and any other contract can interact with it — without knowing anything specific about your implementation.

The standard interface

Six functions and two events. That's the whole standard. Here's what each one does:

Function / Event Purpose
totalSupply() Returns the total number of tokens in existence. Every token minted increases this. Every token burned decreases it.
balanceOf(address) Returns how many tokens a given address holds. This is what MetaMask calls to show you your balance.
transfer(to, amount) Moves tokens from the caller's balance to another address. If the caller doesn't have enough tokens, it reverts.
approve(spender, amount) Gives another address permission to spend up to amount of the caller's tokens on their behalf. Used by DeFi protocols. Covered in detail in Task 3.
allowance(owner, spender) Returns how much a spender is still authorised to transfer from an owner's balance.
transferFrom(from, to, amount) Moves tokens from one address to another, using a previously granted allowance. The caller must have been approved by the from address for at least amount.
Transfer(from, to, amount) (event) Emitted on every token movement — whether from transfer(), transferFrom(), or minting. This is how Etherscan builds a token's complete transaction history.
Approval(owner, spender, amount) (event) Emitted every time approve() is called, recording that an allowance was granted or updated.

Three of these — totalSupply, balanceOf, and transfer — you could write from scratch today with what you already know. The approve / allowance / transferFrom trio is where most explanations lose people, so it gets its own section in Task 3. For now, hold the idea that it exists to let a third contract spend tokens on your behalf — without ever getting your private key.

Decimals: why 1 token isn't stored as 1

The EVM has no concept of decimal numbers. All arithmetic on the blockchain operates on integers. So how do you represent a token balance of 1.5? You don't — you represent it as 1,500,000,000,000,000,000 and agree that the last 18 digits are the fractional part.

This is exactly the same relationship ETH has with wei. When your wallet shows you 1.5 ETH, the blockchain is storing 1,500,000,000,000,000,000 wei. There is no floating point anywhere — the display layer divides by 1018 to show the human-readable number. ERC-20 tokens follow the same convention by default: 18 decimal places. The decimals() function returns 18 unless you override it.

This has a concrete consequence when you write code. To mint one million tokens, you don't pass 1000000 to the mint function. You pass 1000000 * 10 ** 18. Solidity has a helper for this: 

// These are equivalent — both mint 1,000,000 tokens
_mint(msg.sender, 1000000 * 10 ** 18);
_mint(msg.sender, 1000000 * 10 ** decimals());

The second form is preferred because it stays correct if you ever change the decimal count. In practice you won't — 18 is the universal convention, and deviating from it breaks compatibility with most tooling — but using decimals() signals intent more clearly.

When you call balanceOf on a deployed token and get back a large raw number, that number is in the token's smallest unit (equivalent to wei for ETH). Divide by 1018 to get the readable balance. Frontends do this automatically. In Remix you'll see the raw number and have to do the conversion mentally.

Read EIP-20 — Token Standard

The original proposal. Short, well-written, and worth reading once. The rationale section explains exactly why each function exists and what problem it solves. It's also a good example of what a well-specified interface looks like.

Writing a fully compliant ERC-20 from scratch would take several hundred lines and require getting subtleties exactly right — handling edge cases in allowances, emitting the right events in the right places, avoiding integer overflow on transfers. People have done this wrong and lost real money. There is a better approach.

OpenZeppelin

OpenZeppelin is a library of smart contract building blocks written by security-focused engineers, reviewed by professional auditors, and deployed in contracts holding billions of dollars across the ecosystem. Their ERC-20 implementation has been stress-tested in ways no first-year project ever will be.

The right way to think about OpenZeppelin is not as a shortcut but as the correct engineering choice. When you write production software, you don't reimplement string parsing from first principles when a well-maintained library exists. The same logic applies here, and the stakes are higher — a bug in a deployed token contract cannot be patched.

In Remix, you import OpenZeppelin contracts directly from their GitHub repository. The compiler fetches the source automatically: 

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

Inheritance

Before writing the contract, one concept you need: inheritance. When a contract uses is SomeOtherContract, it inherits everything from that contract — all its state variables, all its functions, all its internal logic. Your contract is an extension of it. You get the base behaviour for free and can add to it, or override specific parts. 

// This contract IS an ERC20. It has totalSupply, balanceOf,
// transfer, approve, allowance, transferFrom — all of it — for free.
contract MyToken is ERC20 {
    // Your additions go here
}

OpenZeppelin's ERC20 already implements the complete standard correctly. is ERC20 gives you all of that. You only write what's unique to your specific token: its name, symbol, initial supply, and any custom logic like minting or burning.

Writing the token

Create a new file in Remix called MyToken.sol. Write this out rather than pasting it — the constructor line is where most mistakes happen and typing it forces you to read it carefully: 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.10;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MyToken is ERC20 {
    address public owner;

    constructor(string memory _name, string memory _symbol) ERC20(_name, _symbol) {
        owner = msg.sender;
        _mint(msg.sender, 1000000 * 10 ** decimals());
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "Not the owner");
        _;
    }

    function mint(address _to, uint256 _amount) public onlyOwner {
        _mint(_to, _amount);
    }
}

The constructor has two parameter lists — that's the one thing that looks unusual. (string memory _name, string memory _symbol) are the parameters for your constructor. The ERC20(_name, _symbol) that immediately follows is the call to the parent contract's constructor — it's how you pass the token name and symbol up to OpenZeppelin's code, which stores them. This syntax is specific to inheritance in Solidity: when your contract inherits from another that has a constructor with parameters, you must call the parent constructor this way.

_mint is an internal function from OpenZeppelin's ERC20. It creates tokens — increasing totalSupply by the amount given, adding that amount to the recipient's balance, and emitting the Transfer event from the zero address to the recipient (the conventional way to represent minting in the standard). You cannot call _mint from outside the contract — the leading underscore in OpenZeppelin's naming convention signals that a function is internal. That's exactly what you want: the only way to mint new tokens is through your public mint() function, which is guarded by onlyOwner.

Deploying and testing

Compile with version 0.8.10 or higher. You may see a yellow warning about unused variables — that's fine. Deploy to Remix VM (Shanghai) with the constructor arguments filled in: enter your token name and symbol in the input fields next to the Deploy button. Choose something — you're building your own coin.

After deployment, expand the contract. You'll see a longer list of functions than in previous days — these are all the ERC-20 functions you inherited, plus yours. Work through these steps in order:

  1. Call totalSupply. You'll see a large number — 1000000000000000000000000. That's one million tokens expressed with 18 decimal places. Divide by 1018 and you get 1,000,000.
  2. Call balanceOf with your deployer address (copy it from the Account dropdown at the top of the Deploy panel). It should return the same large number — you got the entire initial supply.
  3. Call name and symbol. They return whatever you passed to the constructor.
  4. Call decimals. It returns 18.
  5. Call transfer with a second Remix account address and an amount of 1000000000000000000 (that's 1018 — exactly 1 token). Switch to the second account and call balanceOf with its address — it should show 1000000000000000000.
  6. Switch back to the deployer account. Call mint with the second account's address and 5000000000000000000 (5 tokens). Check the second account's balance again — it should now be 6000000000000000000.
  7. Switch to the second account. Try calling mint. It should revert with "Not the owner". The onlyOwner modifier is working.

One thing worth noticing in the Remix console after the transfer and mint calls: expand the transaction log and look at the Logs section. You'll see a decoded Transfer event for each one — the from address, the to address, and the value. This is the event data that Etherscan uses to build a token's transaction history. OpenZeppelin's implementation emits these automatically; you don't have to write any event code yourself.

Your token works. Now extend it with two features that appear in almost every production ERC-20 — a burn mechanism and a supply cap — and then work through the approval system properly, because it's the mechanism that makes all of DeFi function and it's consistently misunderstood.

Adding burn

Burning destroys tokens permanently, reducing total supply. It's the opposite of minting. OpenZeppelin provides an internal _burn(address, amount) function that handles everything: decrements the holder's balance, decrements totalSupply, and emits a Transfer event to the zero address (the conventional way to represent a burn in the standard).

The question is who gets to burn tokens. The most common design: any holder can burn their own tokens, but nobody can burn someone else's. A public burn function that burns from msg.sender naturally enforces this — you can only call it on your own behalf. 

function burn(uint256 _amount) public {
    _burn(msg.sender, _amount);
}

That's the entire function. _burn handles the balance check internally — if msg.sender doesn't hold enough tokens, the transaction reverts with a clear error message before any state changes. You don't need a manual require here; OpenZeppelin's implementation already has it.

Adding a supply cap

A cap prevents the owner from minting tokens beyond a fixed maximum. It's a trust mechanism: if users know the maximum supply is capped at 10 million and the contract enforces it, they know their holdings can never be diluted beyond that point. You add the check to the mint function: 

uint256 public constant MAX_SUPPLY = 10_000_000 * 10 ** 18;

function mint(address _to, uint256 _amount) public onlyOwner {
    require(totalSupply() + _amount <= MAX_SUPPLY, "Cap exceeded");
    _mint(_to, _amount);
}

constant means the value is fixed at compile time and never changes — the compiler replaces every reference to MAX_SUPPLY with the literal number, so it costs no storage. The underscores in 10_000_000 are a readability feature added in Solidity 0.8 — the compiler ignores them, but they make large numbers much easier to read at a glance.

The check happens before the mint: if the current totalSupply() plus the requested amount would exceed the cap, the whole transaction reverts. No partial mints.

The approval system

This is the mechanism that almost everyone misunderstands the first time they use DeFi. When you swap tokens on Uniswap, you're not sending your tokens directly to Uniswap's contract. At some point before the swap, you sign a transaction granting Uniswap's contract permission to move a specific amount of your tokens on your behalf. That permission is recorded in your token contract as an allowance. When the swap executes, Uniswap calls transferFrom on the token contract — and the token contract checks whether Uniswap is authorised, then moves the tokens.

Your private key never leaves your wallet. You never sent your tokens to Uniswap. You gave the token contract a signed instruction saying "this specific contract is allowed to spend up to this amount from my balance." That's all approve does.

The full flow in code:

// Step 1: Alice calls this on the token contract
// "I allow Uniswap to spend up to 100 of my tokens"
token.approve(uniswapAddress, 100 * 10 ** 18);

// Step 2: Uniswap's contract calls this when executing Alice's swap
// (Uniswap calls transferFrom on Alice's behalf)
token.transferFrom(aliceAddress, poolAddress, 100 * 10 ** 18);

Inside OpenZeppelin's transferFrom, three things happen: the function checks that the caller (Uniswap's contract) has an allowance of at least 100 tokens from Alice, deducts that amount from the allowance, and then moves the tokens. If Uniswap tries to call transferFrom without Alice having approved it first, the transaction reverts.

This pattern is why DeFi requires two transactions for a first-time token interaction: one approve and one actual operation. You might have noticed this with MetaMask — the first time you use a new protocol with a new token, you approve, then confirm the main transaction. That approval transaction is calling approve() on the token contract.

Testing the approval flow in Remix

  1. Deploy the full contract (with burn and cap) as Account A. Account A starts with the full initial supply.
  2. As Account A, call approve with Account B's address and 500000000000000000000 (500 tokens).
  3. Call allowance with Account A as owner and Account B as spender. It should return 500000000000000000000.
  4. Switch to Account B. Call transferFrom with Account A as the from address, Account B as to, and 100000000000000000000 (100 tokens).
  5. Check Account A's balance — it should have decreased by 100 tokens. Check the allowance again — it should now be 400 tokens. Account B consumed part of its allowance.
  6. As Account B, try to call transferFrom with an amount of 500 tokens — more than the remaining allowance of 400. It should revert.
  7. As Account A, call burn with 1000000000000000000000 (1,000 tokens). Call totalSupply — it should have decreased by exactly that amount.
  8. Try minting up to the cap: call totalSupply, calculate how much is left before hitting MAX_SUPPLY, and try to mint that plus one token more. It should revert with "Cap exceeded".

The complete contract

Here is everything together. Read through it before deploying — every line should be familiar by now, and anything that isn't is worth pausing on: 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.10;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MyToken is ERC20 {
    address public owner;
    uint256 public constant MAX_SUPPLY = 10_000_000 * 10 ** 18;

    constructor(string memory _name, string memory _symbol) ERC20(_name, _symbol) {
        owner = msg.sender;
        _mint(msg.sender, 1_000_000 * 10 ** decimals());
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "Not the owner");
        _;
    }

    function mint(address _to, uint256 _amount) public onlyOwner {
        require(totalSupply() + _amount <= MAX_SUPPLY, "Cap exceeded");
        _mint(_to, _amount);
    }

    function burn(uint256 _amount) public {
        _burn(msg.sender, _amount);
    }
}

This is a real, deployable ERC-20 token. It follows the standard, it inherits a battle-tested implementation, it has an owner-gated mint with a hard cap, and any holder can burn their own balance. In Day 6 you deploy this exact contract to the Sepolia testnet, verify it on Etherscan, and import it into MetaMask so it appears in your wallet alongside any other token you hold.
