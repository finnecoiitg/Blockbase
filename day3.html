Day 3

Solidity Basics

From today, the course shifts from reading about blockchains to building on them. That means writing Solidity — the programming language that compiles to EVM bytecode and runs on every Ethereum node simultaneously.

If you've written JavaScript, Python, or C++ before, the syntax will look familiar. If you haven't written code before, the structure is straightforward enough to follow. What makes Solidity genuinely unusual isn't the keywords — it's the environment. Every write operation costs real money. Deployed code can never be changed. There is no exception handler that notifies someone when things go wrong. Those constraints aren't just quirks; they show up in how the language is designed and in every pattern you'll use.

The file header

Every Solidity file must begin with two lines before any contract code: 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.10;

The first is the license identifier. Tools like Etherscan and package managers use it to categorise and verify your contract. The Solidity compiler will issue a warning if you omit it. For this course, MIT is always the right choice — it's the standard permissive licence for open-source contracts.

The second is the pragma — a compiler directive that specifies which version of Solidity you're targeting. ^0.8.10 means "version 0.8.10 or any higher minor or patch version, but not 0.9.x." This matters because the language changes between major versions. Version 0.8 introduced a particularly important safety change: checked arithmetic. Before 0.8, adding 1 to the maximum value of a uint256 would silently wrap around to 0 — a class of bug responsible for real money losses in deployed contracts. In 0.8 and later, that operation reverts the transaction rather than corrupting data silently. Use 0.8.x for everything you write on this course.

What a contract is

A contract is the fundamental unit of Solidity code. It groups together state variables and the functions that operate on them — structurally similar to a class in object-oriented languages. 

contract HelloWorld {
    // state variables and functions go here
}

When you deploy a contract, it's compiled to bytecode and stored at a newly created address on the blockchain. That address is permanent. The code at it is permanent. You can send ETH to it, call its functions, build other contracts that talk to it — but you cannot change the code after deployment, and you cannot delete it. Whatever you deploy is what exists, forever. This is why testing before deployment matters more in Solidity than in almost any other programming environment you'll encounter.

Variables on the blockchain

Solidity has three distinct categories of variable, and understanding the difference between them is more important than memorising any particular syntax. 

contract Variables {
    // ── STATE variables ───────────────────────────────────────────
    // Declared at the contract level. Stored permanently on-chain.
    uint public myNumber = 42;
    string public myName = "BlockBase";
    bool public isActive = true;

    function doSomething() public {
        // ── LOCAL variable ────────────────────────────────────────
        // Exists only while this function runs. Never stored on-chain.
        uint localVar = 10;

        // ── GLOBAL variables ──────────────────────────────────────
        // Injected by the EVM. No declaration needed.
        address sender = msg.sender;       // who called this function
        uint timestamp = block.timestamp;  // Unix time of the current block
    }
}

State variables are declared at the contract level — not inside any function. They live in the contract's storage slot on the blockchain and persist between every call. When a function writes to a state variable, that write becomes part of a transaction, gets included in a block, and is permanently recorded. A week later, from a different computer, a different person calls a view function that reads that variable — it returns exactly what was stored a week ago. State variables are the reason smart contracts can maintain data between interactions without any external database. Writing to them costs gas. Reading them is free.

Local variables are declared inside a function body and exist only for the duration of that function call. When the function returns, they're gone — they're never written to the blockchain and cost almost nothing to use. They behave just like variables in any other language.

Global variables aren't declared anywhere — they're built into the EVM and available in every function without any import or setup. The two you'll use constantly are msg.sender and block.timestamp. msg.sender is the address of whoever called the current function — a wallet address if a user called it directly, a contract address if another contract made the call. block.timestamp is the Unix timestamp of the block being validated. These let your contract know who is interacting with it and when — two pieces of information you have no other way to obtain.

Data types

The core types you'll use throughout this course:

uint / uint256
Unsigned integer — a non-negative whole number, from 0 to 2256−1. uint is an alias for uint256. There's no generic "number" type in Solidity — integers are always sized explicitly. You'll use uint for most things: balances, counts, token amounts, and any quantity that can't be negative.
int / int256
Signed integer — can be negative. Range is −2255 to 2255−1. Less common than uint in practice because most quantities in smart contracts are non-negative by definition. Use it when you genuinely need negative numbers — temperature values, relative changes, offsets.
bool
true or false. Used for flags and on/off states. Common examples: bool public paused to freeze a contract in an emergency, bool public isEnrolled to track membership.
address
A 20-byte Ethereum address — the 0x... identifier of a wallet or contract. This type has no direct equivalent in most other languages. You'll use it constantly: storing who owns something, who deployed the contract, or whose address is allowed to call a restricted function. The address payable variant can receive ETH.
string
Arbitrary-length text. Solidity's string handling is limited compared to most languages — concatenation, length checks, and comparisons all require workarounds. More importantly, storing strings on-chain is expensive because storage is priced per byte. Short strings (names, labels, short messages) are fine. Long text belongs off-chain (on IPFS, for example), with only a hash stored in the contract.
bytes32
A fixed-size 32-byte value. More gas-efficient than string for short, bounded data. Commonly used for identifiers, hashes, and names where the maximum length is known. You'll see it frequently in production contracts and in OpenZeppelin's library code.

Visibility

Every state variable and every function in Solidity must have a visibility modifier. It controls who can read the variable or call the function.

public
For state variables, Solidity automatically generates a getter function — anyone can call contractAddress.myVariable() to read it. For functions, anyone can call it from outside the contract and from within it. Use public for anything you want accessible to users, frontends, or other contracts.
private
Accessible only from within this contract's own functions — not from child contracts, not from external callers. One important caveat: private does not mean the data is secret. Everything on the blockchain is readable by anyone who queries the raw storage slots directly. private only removes the auto-generated getter function; it does not encrypt or hide the value in any way.
internal
Like private, but accessible to contracts that inherit from this one. This is the implicit default for state variables when you specify no modifier — though you should always be explicit. Used heavily in base contracts and libraries that are meant to be extended.
external
Functions only — cannot be applied to state variables. An external function can only be called from outside the contract, not from within it. It's marginally more gas-efficient than public for functions never called internally, because the compiler can optimise how arguments are handled. Common in interface definitions.

Functions and gas

The most consequential distinction in Solidity functions is whether they change the blockchain's state. This determines whether calling them costs gas. 

contract Counter {
    uint public count = 0;

    // No modifier → changes state → transaction required → costs gas
    function increment() public {
        count = count + 1;
    }

    // view → reads state, cannot write it → no transaction → free
    function getCount() public view returns (uint) {
        return count;
    }

    // pure → reads nothing, writes nothing → no transaction → free
    function add(uint a, uint b) public pure returns (uint) {
        return a + b;
    }
}

A regular function — one with no view or pure keyword — can read and write state variables. Calling it requires broadcasting a transaction to the network, having it included in a block, and paying gas. The state change is permanent once the block is confirmed. This is a real operation with real cost and real consequences.

A view function can read state but cannot modify it. The compiler enforces this strictly — if you try to write to a state variable inside a view function, it won't compile. Calling a view function doesn't require a transaction. Your node (or a provider like Infura or Alchemy) executes the code locally and returns the result. No gas, no waiting for confirmation, no MetaMask popup. This is why reading data on Etherscan is instant and free — the node just runs the view function and hands back the result.

A pure function cannot read or write state at all. It operates only on its inputs. Use it for utility logic: mathematical operations, format conversions, validation that doesn't need to look at any stored data. Like view functions, calling them costs nothing.

A practical rule: if you're writing a function that reads data and returns something without changing anything, mark it view. If it doesn't touch contract storage at all, mark it pure. The compiler will warn you if your annotation is inconsistent with what the function actually does.

Control flow

Solidity's control flow looks like JavaScript or C. The syntax is familiar; a few Solidity-specific details are worth noting. 

// Conditionals
function describe(uint x) public pure returns (string memory) {
    if (x < 10) {
        return "small";
    } else if (x < 100) {
        return "medium";
    } else {
        return "large";
    }
}

// For loop
function sumToN(uint n) public pure returns (uint) {
    uint total = 0;
    for (uint i = 1; i <= n; i++) {
        total = total + i;
    }
    return total;
}

Notice the string memory return type. Strings in Solidity require a data location specifier because they're dynamically sized. The rule: whenever you return a string, a struct, or an array from a function, write memory after the type name. The compiler will tell you when you forget — it won't compile without it.

One trap that catches people coming from other languages: uint values cannot go below zero. If a uint loop counter reaches 0 and you decrement it again, Solidity 0.8 will revert rather than wrapping around to a large number. When you need to count downward, either restructure the loop to count upward, or use a signed integer. You'll encounter this the first time you try to write a descending loop.

Setting up Remix

Remix is a browser-based IDE for Solidity — no installation, no local setup, no Node.js environment to configure. Go to remix.ethereum.org. Use Chrome, Firefox, or Brave. Do not use Safari — MetaMask doesn't work as a browser extension on it.

The interface has three areas you'll work in constantly:

  • Left sidebar — File Explorer (your .sol files), Solidity Compiler (turns your code into bytecode), and Deploy & Run (sends contracts to the VM or to a real network via MetaMask).
  • Editor (centre) — where you write code. It has syntax highlighting and real-time error detection — red underlines appear as you type for syntax errors, yellow for warnings.
  • Console (bottom) — transaction logs, compilation errors, and return values from function calls. Every deploy and every state-changing function call produces a log entry here. Green ticks mean success; red circles mean the transaction reverted.

Remix comes with a few example contracts pre-loaded. Open contracts/1_Storage.sol and read through it before writing anything. It stores a single number and has a set and get function — a minimal example of the pattern you're about to build on.

Writing MyStorage

In the File Explorer (left sidebar), click the new file icon and name it MyStorage.sol. Then write the following contract — typing it out rather than pasting is worth the few extra minutes: 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.10;

contract MyStorage {
    uint public storedNumber;
    string public storedMessage;
    address public lastCaller;

    function setNumber(uint _number) public {
        storedNumber = _number;
        lastCaller = msg.sender;
    }

    function setMessage(string memory _message) public {
        storedMessage = _message;
        lastCaller = msg.sender;
    }

    function getNumber() public view returns (uint) {
        return storedNumber;
    }
}

Read through it before deploying. There are three state variables: storedNumber, storedMessage, and lastCaller. All three are public, which means Solidity generates getter functions for each — Remix will show them as blue read buttons after deployment.

The two setter functions each take a parameter (prefixed with _ by convention, to distinguish function parameters from state variables that share the same name) and write it to storage. They also record msg.sender in lastCaller — so you can always see which address most recently wrote to the contract.

getNumber() is marked view because it only reads storedNumber and returns it. It doesn't need to be a separate function — since storedNumber is public, the auto-generated getter does the same thing — but writing it explicitly is good practice for understanding which functions are free to call.

Compiling and deploying

  1. Click the Solidity Compiler tab in the left sidebar (the icon looks like an S shape). Select compiler version 0.8.10 or any higher 0.8.x. Click Compile MyStorage.sol. A green checkmark means success. A red circle means a syntax error — look at the console panel for the exact line number and description.
  2. Click the Deploy & Run tab (the Ethereum diamond icon). Under Environment, select Remix VM (Shanghai) — this is a local in-browser simulation with fake ETH. No real network, no MetaMask, instant transactions.
  3. Under Contract, confirm MyStorage is selected. Click Deploy. The contract appears under "Deployed Contracts" in the bottom-left panel with its simulated address. Click the arrow to expand it.

What just happened: the compiled bytecode was sent as a transaction to the VM's simulated blockchain. The VM assigned it a new contract address. That contract now exists at that address and responds to calls — the same way a real deployed contract does, just without a live network involved.

Interacting with your contract

With the deployed contract expanded, you'll see orange and blue buttons. Orange buttons trigger state-changing functions — they go through a simulated transaction and produce a log entry in the console. Blue buttons call view functions or read public state variables — they're instant and free.

  • Click setNumber, type 42 in the input box, and click the button. The console shows a green-tick transaction log.
  • Click getNumber — it returns 42. The number is now stored permanently in the simulated blockchain's state.
  • Click setMessage, type "Hello from BlockBase" (include the quote marks), and submit.
  • Click storedMessage — your string is returned.
  • Click lastCaller — it shows the address that last wrote to the contract. Look at the Account dropdown at the top of the Deploy panel; it should be the same address.
  • Switch to a different account in the Account dropdown. Call setNumber with a new value. Click lastCaller again — it now shows the new address.

That last step is the key thing to notice: msg.sender is not a fixed value — it reflects whoever sent the current transaction. The contract automatically tracks which account last modified its state, with no manual passing of addresses required.

You can write, deploy, and interact with a basic contract. Before the challenge, two more tools that appear in nearly every real Solidity contract: the constructor and require().

Constructors

A constructor is a special function that runs exactly once — at the moment the contract is deployed — and never again. It's the contract's setup code: a place to initialise state variables and capture information that's only available at deployment time. 

contract Owned {
    address public owner;

    constructor() {
        owner = msg.sender;
    }
}

When this contract is deployed, msg.sender is the deployer's address. The constructor captures it immediately and stores it in owner. After that, the deployer's address is permanently recorded on-chain and available to every function in the contract for as long as the contract exists. There's no other way to capture the deployer's address — by the time any other function runs, msg.sender will be whoever called that function, not whoever deployed the contract.

Constructors can also take parameters for configuring the contract at deployment time: 

contract Configurable {
    uint public maxSupply;

    constructor(uint _maxSupply) {
        maxSupply = _maxSupply;
    }
}

When you deploy this in Remix, a text field appears next to the Deploy button asking for the _maxSupply value. Whatever you enter is stored permanently when the contract goes live. The constructor runs once and is gone — it cannot be called again later.

require()

require() is how you enforce preconditions. It takes a boolean condition and an error message. If the condition is false, the entire transaction reverts: no state changes, the error message is returned to the caller, and the gas used up to the revert point is charged (the rest is refunded). 

function withdraw(uint _amount) public {
    require(_amount > 0, "Amount must be positive");
    require(_amount <= balance, "Insufficient balance");

    balance -= _amount;
    // transfer logic here
}

Both require checks must pass before the function does anything to state. If the first one fails — say, _amount is 0 — the function stops immediately. balance is never touched. The caller gets the message "Amount must be positive" back and a partial refund. If the first check passes but the second fails, same thing — everything reverts as if the call never happened.

This is the primary pattern for input validation and access control in Solidity. The structure is always the same: check all preconditions at the top of the function, run the logic only if every check passes. You'll use it in nearly every function you write.

The Counter challenge

Build this contract from scratch in Remix — without copying the solution below. Use only what you've learned in Tasks 1, 2, and 3. If you get stuck on a specific piece, re-read the relevant section before looking at the answer. 

Contract: Counter

State variables:
  count  — uint, starts at 0
  owner  — address, set to the deployer at deployment

Functions:
  increment()  — adds 1 to count
  decrement()  — subtracts 1 from count; reverts if count is already 0
  reset()      — sets count back to 0; only the owner can call this
  getCount()   — returns the current count (view function)

Three things to work out on your own before looking below:

  • How does the contract know who the owner is? The deployer's address needs to be captured exactly once, at a specific moment.
  • How does decrement() prevent underflow when count is 0? A uint can't go below zero — you need to stop the function before it tries.
  • How does reset() check that only the owner can call it? You have access to the current caller's address and the stored owner address.

When you're ready to check your work:

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.10;

contract Counter {
    uint public count;
    address public owner;

    constructor() {
        owner = msg.sender;
    }

    function increment() public {
        count = count + 1;
    }

    function decrement() public {
        require(count > 0, "Counter is already at zero");
        count = count - 1;
    }

    function reset() public {
        require(msg.sender == owner, "Only the owner can reset");
        count = 0;
    }

    function getCount() public view returns (uint) {
        return count;
    }
}

Deploy this and test the failure paths — not just the happy path. Increment several times, then decrement back to 0, then try one more decrement: it should revert with your error message. Switch to a different account in the Accounts dropdown and try calling reset(): it should also revert. Switch back to the deployer account and call reset(): it should succeed and set count back to 0.

Testing the cases that should fail is as important as testing the ones that should succeed. In production contracts, the failure paths are exactly where exploits live.
