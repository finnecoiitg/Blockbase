Day 6

Deploying to a Real Network

Everything you have built so far — counters, voting contracts, ERC-20 tokens — has run inside Remix VM. Remix VM is a sandboxed JavaScript simulator that lives entirely in your browser. It has no real blockchain behind it. The accounts are fake, the ETH is fake, and when you close the tab, every deployed contract disappears. It is the right tool for writing and testing code. It is the wrong tool for anything you want to actually exist.

Today you take your ERC-20 token from Day 5 and deploy it to Sepolia — a real Ethereum testnet. After today, your contract will have a permanent address on a live blockchain. Anyone in the world can interact with it. It will persist after you close the browser.

What is a testnet?

A testnet is a complete, live copy of the Ethereum network that runs in parallel with the main one. It uses the same EVM, the same consensus rules, the same transaction format, and the same tooling. The only difference: the ETH on it has no monetary value. You can get it for free from a faucet.

This matters a great deal. Every deployment you make to a real network costs gas. On mainnet, gas costs real money. A botched deployment, a contract with a bug that needs redeployment, a test you forgot to run — these are expensive mistakes on mainnet. On a testnet they cost nothing, and the process is identical in every technical sense. Professionals always test on a testnet before touching mainnet.

Environment Real ETH? Persistent? Use case
Remix VM No — simulated No — lost on tab close Writing and unit-testing code quickly
Sepolia testnet No — free from faucet Yes — lives on a real blockchain Full integration testing, sharing with others, practising deployment
Ethereum mainnet Yes — real money Yes — permanent Production contracts only

Sepolia is the current recommended testnet for Ethereum development. An older testnet called Goerli was widely used until 2023 but is now deprecated — ignore it if you see it in older tutorials. Use Sepolia for everything.

What actually happens when you deploy

In Remix VM, clicking Deploy is instant and frictionless. On a real network, deploying a contract is a transaction — the same kind of transaction as sending ETH, but with one difference: instead of specifying a recipient address, you leave the to field empty and put your compiled contract bytecode in the data field.

The network processes this transaction like any other. A validator picks it up, includes it in a block, and the EVM executes it. During execution, the EVM runs the constructor, allocates storage, and assigns the contract a new permanent address — derived deterministically from the deployer’s address and their transaction count (the nonce). Once the block is finalised, the contract exists at that address on the blockchain forever. There is no delete.

The deployer pays gas for all of this. The cost depends on how much EVM computation the deployment takes — contracts with large constructors or that initialise a lot of storage cost more. Your ERC-20 token will cost a modest amount of Sepolia ETH, which you will get from a faucet.

Bytecode vs source code

When Remix compiles your Solidity, it produces two things. The first is bytecode: low-level hexadecimal instructions that the EVM executes directly, with no human-readable structure. This is what actually gets stored on-chain. The second is the ABI (Application Binary Interface): a JSON description of your contract’s functions and their input/output types, which frontends and tools use to interact with the deployed bytecode.

Your Solidity source code is not stored on-chain. Bytecode is. This means that after deployment, anyone can see the raw bytecode at your contract’s address — but they cannot read what it does unless you separately publish the source code. This is what Etherscan verification does.

Etherscan and block explorers

Etherscan is a block explorer: a website that indexes the entire Ethereum blockchain and presents it in a human-readable format. For any address — wallet or contract — Etherscan shows every transaction ever sent to or from it, every token held, every internal call, and every event emitted.

Sepolia has its own Etherscan instance at sepolia.etherscan.io. The interface is identical to mainnet Etherscan. After you deploy, you will paste your contract address here and see everything about it: the deployment transaction, the deployer’s address, the bytecode, and — after verification — the full readable Solidity source.

An unverified contract on Etherscan shows only bytecode under its Contract tab, with a banner reading “Contract source code not verified.” A verified contract shows the full Solidity, a readable function list under Read Contract and Write Contract, and a green checkmark. In real projects, verification is expected — a deployed contract that nobody can read is a red flag.

Explore Sepolia Etherscan

Open this now and search for any contract address. Look at a verified contract — find the Contract tab, the Read Contract tab, and the transaction list. This is what your contract will look like after today.

Step 1 — Open MyToken.sol in Remix

Go to remix.ethereum.org and open the MyToken.sol file you wrote in Day 5. If you no longer have it, here is the complete contract: 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.10;

import "@openzeppelin/contracts/token/ERC20/ERC20.sol";

contract MyToken is ERC20 {
    address public owner;
    uint256 public constant MAX_SUPPLY = 10_000_000 * 10 ** 18;

    constructor(string memory _name, string memory _symbol) ERC20(_name, _symbol) {
        owner = msg.sender;
        _mint(msg.sender, 1_000_000 * 10 ** decimals());
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "Not the owner");
        _;
    }

    function mint(address _to, uint256 _amount) public onlyOwner {
        require(totalSupply() + _amount <= MAX_SUPPLY, "Cap exceeded");
        _mint(_to, _amount);
    }

    function burn(uint256 _amount) public {
        _burn(msg.sender, _amount);
    }
}

Compile it. Use version 0.8.10 or higher. Make sure there are no red errors — yellow warnings are fine.

Step 2 — Switch the deployment environment

In Remix, open the Deploy & Run Transactions tab (the icon that looks like a stack of blocks with a play button). At the top you will see an Environment dropdown currently set to “Remix VM (Shanghai)” or similar. Click it and select “Injected Provider — MetaMask”.

MetaMask will immediately pop up asking to connect to Remix. Click Connect. After connecting, check two things in Remix:

  1. The Account field now shows your MetaMask wallet address instead of a fake Remix account.
  2. The network indicator shows Sepolia. If MetaMask is on a different network, switch it to Sepolia first (MetaMask → network selector at the top → Sepolia Test Network). Remix will update automatically.

You should also see a small ETH balance next to your account address in Remix — that is your real Sepolia ETH balance, pulled live from the network.

Step 3 — Deploy

Scroll down to the Deploy section. You will see two input fields next to the Deploy button: one for _name and one for _symbol. These are the constructor parameters. Enter whatever you want — choose a name and symbol for your token.

Click Deploy. MetaMask will pop up showing a transaction summary including the estimated gas fee in Sepolia ETH. Review it, then click Confirm.

Remix shows a pending spinner in the console at the bottom. After 15–30 seconds, the transaction is mined and the spinner becomes a green checkmark. Your deployed contract appears in the Deployed Contracts section at the bottom of the panel, with its address.

Copy that address. It is your token’s permanent address on Sepolia. Save it somewhere — you will need it in Task 3 and in Day 7.

Step 4 — Find your contract on Etherscan

Go to sepolia.etherscan.io and paste your contract address into the search bar. You should see:

  1. Your contract address, labeled as a contract (not a wallet address).
  2. One transaction in the history — the deployment transaction, with your wallet address as the “From”.
  3. Under the Contract tab: bytecode, and a banner saying the source code is not verified.

This is exactly correct. The contract is live but unverified. Task 3 fixes that.

Explore Sepolia Etherscan

Find your deployment transaction. Click into it and examine the fields: the block it was included in, the gas used, the input data (your contract’s bytecode). The “To” field will show “Contract Creation” — that is what a deployment transaction looks like at the network level.

Your contract is live. This task covers three things: verifying the source code on Etherscan so others can read it, importing the token into MetaMask so it shows up in your wallet, and interacting with classmates’ contracts using Etherscan’s built-in interface.

Verifying on Etherscan

Verification is the process of submitting your Solidity source code to Etherscan, which recompiles it and confirms the resulting bytecode matches what is stored at your contract’s address. If they match, Etherscan publishes the source code publicly and marks the contract as verified.

This is not about trust in Etherscan specifically. It’s about giving anyone who interacts with your contract the ability to audit what it actually does. A contract that holds other people’s tokens and cannot be read is a contract nobody should trust.

Follow these steps exactly:

  1. On your contract’s Etherscan page, click the Contract tab (between Transactions and Events). You will see the raw bytecode and a button labelled “Verify and Publish”. Click it.
  2. Compiler Type: Select Solidity (Single file). Your contract imports from OpenZeppelin, but Remix flattens those imports when you use the single-file option — you will paste the entire flattened source.
  3. Compiler Version: This must match exactly what you compiled with in Remix. If you used 0.8.10, pick v0.8.10+commit.fc410830. Check Remix’s compiler tab to confirm which version was used.
  4. Open Source License Type: Select MIT License (MIT).
  5. Click Continue.
  6. In the source code box, you need to paste a flattened version of your contract — one that inlines the OpenZeppelin imports rather than referencing them. In Remix, right-click your MyToken.sol file in the file explorer and select “Flatten”. This creates a MyToken_flat.sol file with all imports merged. Copy its entire contents and paste it into the Etherscan source code box.
  7. Leave the Constructor Arguments field empty — Etherscan usually detects them automatically from the deployment transaction.
  8. Click Verify and Publish. After 30–60 seconds, you will see a success page.

Return to your contract’s main Etherscan page and refresh. The Contract tab now shows your full Solidity source. You will also see two new sub-tabs: Read Contract and Write Contract.

Read Contract and Write Contract

These two tabs are Etherscan’s built-in interface for interacting with your deployed contract — without needing to return to Remix.

Read Contract shows all your view and pure functions: functions that only read state and cost no gas. You can call them directly from the browser — no wallet required, no transaction, instant results. Try calling totalSupply, name, symbol, and balanceOf with your own address.

Write Contract shows all state-changing functions. To use them you need to connect your wallet — click “Connect to Web3” at the top of the Write Contract tab and approve the MetaMask popup. From here you can call transfer, mint, burn, and approve directly on your live Sepolia contract. Each call opens MetaMask to confirm a real transaction.

Importing your token into MetaMask

By default MetaMask only tracks ETH. To see your token balance in the wallet, you need to tell MetaMask where to look.

  1. Open MetaMask. Make sure you are on the Sepolia network.
  2. Scroll down in the Assets tab until you see “Import tokens”. Click it.
  3. Paste your token’s contract address. MetaMask will automatically fetch the token symbol and decimal count from the contract.
  4. Click Next, then Import.

Your token now appears in MetaMask alongside Sepolia ETH. The balance shown is the 1,000,000 tokens minted to your address at deployment. This is exactly what MetaMask does when it calls balanceOf on your contract — everything you wrote in Day 5 is now powering a live wallet display.

Interact with a classmate’s token

Share your Etherscan link in the group chat and find someone else’s contract. Open their Etherscan page — because they have verified their contract, you can read exactly what it does before interacting with it.

  1. Go to their Read Contract tab. Call balanceOf with your own wallet address. You hold 0 of their token — you have not received any.
  2. Ask them to use Write Contract on their own page to call transfer with your address and a small amount (remember: amounts are in the smallest unit, so 1 token = 1000000000000000000).
  3. After their transaction is mined, call balanceOf again with your address. You now hold some of their token.
  4. Import their token into your MetaMask the same way you imported your own. It appears in your wallet alongside yours.

This is the ERC-20 standard working in practice. Two different tokens, two different contracts, both imported and displayed in the same wallet without any custom code — because they both implement the same interface.

Hardhat: what professionals use instead of Remix

Remix is excellent for learning and for quick prototyping. Production projects use a different tool: Hardhat. You will not use it in this course, but you will see it everywhere — in tutorials, in job descriptions, in every serious open-source contract repository — so here is what you need to know about it.

Hardhat is a Node.js development environment for Ethereum. It runs on your local machine and gives you a local blockchain (faster than Remix VM), a test runner, and deployment scripts. Contracts live in a /contracts folder. Tests live in a /test folder and are written in JavaScript using the Mocha and Chai testing libraries.

The three commands you will encounter most often:

# Create a new Hardhat project in an empty folder
npx hardhat init

# Compile all .sol files in the /contracts folder
npx hardhat compile

# Run all test files in the /test folder
npx hardhat test

A typical Hardhat test looks like this:

const { expect } = require("chai");

describe("MyToken", function () {
  it("Should mint 1 million tokens to the deployer", async function () {
    const [owner] = await ethers.getSigners();
    const MyToken = await ethers.getContractFactory("MyToken");
    const token = await MyToken.deploy("BlockBase Token", "BBT");

    const balance = await token.balanceOf(owner.address);
    expect(balance).to.equal(ethers.parseUnits("1000000", 18));
  });
});

The pattern is straightforward: deploy the contract inside the test, call its functions, and assert that the results match what you expect. If they don’t, the test fails and shows you exactly which assertion failed. For a real project with multiple contracts, dozens of edge cases, and real money at stake, this kind of automated test suite is not optional.

You will not write Hardhat tests in this course. But after Day 8, when you explore further on your own, Hardhat is the right next step.
