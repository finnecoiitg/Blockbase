Day 8

Capstone Project

Day 8 is the full development loop in a single session: smart contract, Sepolia deployment, Etherscan verification, and a browser frontend. Choose one of the three options below, read through its entire tab before writing any code, then build and demo.

Choosing your option

All three options apply every skill from Days 3–7: Solidity, OpenZeppelin inheritance, Remix, Sepolia testnet, ethers.js, and MetaMask. The difference is what the contract does.

Option What it builds Core concept Good if you’re interested in
A Token Voting Dashboard approve + transferFrom, weighted governance DeFi, DAOs, protocol governance
B NFT Minter ERC-721, payable functions, on-chain metadata Digital ownership, NFTs, creative applications
C Decentralised Fundraiser ETH handling, time-based logic, refund pattern Real-world finance, crowdfunding, community tools

What every project must include

Regardless of which option you choose, your submission must satisfy all four of these:

  • Deployed on Sepolia — a working contract address visible on sepolia.etherscan.io
  • Verified source code — the full Solidity visible on Etherscan’s Contract tab (same process as Day 6)
  • Working frontend — a browser HTML file that connects via MetaMask and performs at least one state-changing transaction
  • Live demo — you show it working in front of the room

What separates a strong project

Beyond the requirements above, strong projects tend to have three qualities:

  • Robust contract logic — edge cases handled with require statements, events emitted for every state change, error messages that tell you exactly what went wrong
  • Responsive frontend — the user always knows what is happening: loading states while transactions confirm, clear success and error messages, relevant data that updates after each interaction
  • Clean presentation — you can explain what your contract does, point to it on Etherscan, and name one thing you would add next

Before you start

Have these ready before writing any code:

  • MetaMask installed and set to Sepolia testnet
  • At least 0.05 SepoliaETH — enough for deployment plus several test transactions. Refill at sepoliafaucet.com or the QuickNode faucet
  • Remix IDE open in a browser tab
  • Your Day 6 ERC-20 contract address ready (only needed for Option A)
  • A plain text editor for writing the HTML frontend
Tip

Read the full tab for your chosen option before writing any code. Understanding the complete picture first prevents you from having to rewrite logic partway through.

Option A is a governance-style voting dApp where participants cast weighted votes by committing ERC-20 tokens. The candidate with the highest accumulated token-weight wins. Token-weighted governance is the mechanism Uniswap, Compound, Aave, and MakerDAO use for protocol decisions — this is a simplified version of that architecture.

How it works

The owner deploys the voting contract and passes the address of an existing ERC-20 token. The owner adds candidates. To vote, a participant calls approve on the token contract to authorise the voting contract to spend some of their tokens, then calls vote() — which pulls the approved tokens into the voting contract and records the weight. When the owner closes voting, the winner is the candidate with the highest accumulated token-weight.

Prerequisite

This option requires your deployed ERC-20 contract from Day 6. You will pass that contract’s address to the voting contract constructor. If you cannot find it, check your Remix history, or deploy a fresh token from your Day 5 code first.

Your contract: TokenVoting.sol

Create TokenVoting.sol in Remix. Design the storage layout, events, and all function logic yourself to satisfy these requirements:

  • Accept an ERC-20 token address at deployment. Import IERC20 from OpenZeppelin (@openzeppelin/contracts/token/ERC20/IERC20.sol). Voting weight equals the number of tokens a voter commits.
  • The owner can add candidates (name + description) while voting is open. Only the deploying address should be able to do this.
  • Token holders vote by committing tokens to one candidate. Each address may vote only once. Tokens are pulled from the caller using transferFrom — the voter must have already approved the voting contract on the token.
  • The owner can close voting. The winner is the candidate with the highest accumulated token weight.
  • Emit events to record when a candidate is added, when a vote is cast, and when voting closes. Decide yourself what data each event should carry.
  • Your contract must expose these exact function signatures (the frontend template calls them by name):
    • addCandidate(string name, string description)
    • vote(uint256 candidateId, uint256 amount)
    • closeVoting()
    • getCandidateCount() view returns (uint256)
    • getCandidate(uint256 id) view returns (string name, string description, uint256 totalVotes)
    • getWinnerId() view returns (uint256)
    • votingOpen() view returns (bool)
    • hasVoted(address) view returns (bool)

Implementation guide

IERC20 interface. Instead of importing the full ERC-20 implementation, the contract imports only the IERC20 interface — the minimum set of signatures needed to call transferFrom. This lets the voting contract work with any standard ERC-20 token, not just one specific implementation.

The vote flow. vote() calls voteToken.transferFrom(msg.sender, address(this), _amount). This only works if the voter has already called approve(votingContractAddress, amount) on the token contract. Without the prior approval, the transfer reverts. This two-step approve → transferFrom pattern is the standard ERC-20 mechanism for letting another contract spend your tokens — the same one you studied on Day 5.

Error message prefixes. Each require includes the contract name as a prefix ("TokenVoting: ..."). When a reverted transaction lands in your frontend, this tells you immediately which contract rejected it — essential once you have multiple contracts involved.

Internal naming convention. _getWinnerId uses a leading underscore to signal it is an internal helper, not a public interface. This is a Solidity convention rather than a compiler rule, but it makes the distinction between public and internal functions immediately legible.

Full project workflow

  1. Write the contract. Create TokenVoting.sol in Remix and implement every function from the specification above.
  2. Compile. Open the Solidity Compiler tab, select version 0.8.10 or higher, and click Compile TokenVoting.sol. Fix all errors before continuing.
  3. Quick local test. Switch the environment to Remix VM and deploy with a dummy address (0x0000000000000000000000000000000000000001). Call addCandidate("Alice", "Candidate A") and check getCandidateCount() returns 1. This confirms basic logic works before spending testnet gas.
  4. Deploy to Sepolia. Switch to Injected Provider – MetaMask, confirm Sepolia is selected, paste your Day 6 ERC-20 address into the constructor field, and click Deploy. Copy the deployed contract address from Remix.
  5. Add candidates. Call addCandidate two or three times with different names and descriptions. Confirm each MetaMask transaction.
  6. Test voting. On your ERC-20 contract (open it in a second Remix tab or via Etherscan Write Contract), call approve(votingContractAddress, 100000000000000000000) (100 tokens in wei). Then on the voting contract call vote(0, 100000000000000000000). Read hasVoted(yourAddress) — it must return true.
  7. Close voting. Call closeVoting() and verify getWinnerId() returns the correct candidate index.
  8. Verify on Etherscan. Open the contract on sepolia.etherscan.io, go to the Contract tab, and verify the source (same process as Day 6).
  9. Build the frontend. Copy the template below into a new file voting-dapp.html and replace both address constants at the top with your deployed addresses.
  10. Implement castVote(). Complete the stub in the frontend template using what you know from Days 5–7 about ethers.js contract calls.
  11. Live test. Open voting-dapp.html in a browser, connect MetaMask on Sepolia, and run through a full vote cycle from the UI.
Before voting

On your ERC-20 contract (in Remix or via Etherscan Write Contract), call approve(votingContractAddress, amount) before calling vote(). To approve 100 tokens enter 100000000000000000000 (100 × 1018). Your frontend handles this step automatically for the user.

Option B is an NFT minting dApp where anyone can mint a unique on-chain token with a custom name. Unlike ERC-20 where every token is identical, each ERC-721 token has a unique ID and can carry distinct data. CryptoPunks, Bored Apes, and ENS domain names are all ERC-721 contracts.

How it works

Minting requires a small ETH payment per token (0.001 Sepolia ETH by default — trivial for testing but it teaches the payable pattern). The user enters a name, confirms the transaction in MetaMask, and receives a unique NFT with an incremental token ID. The name and timestamp are stored on-chain. The owner can withdraw accumulated ETH from the contract at any time.

Your contract: BlockBaseNFT.sol

Create BlockBaseNFT.sol in Remix. Inherit from OpenZeppelin’s ERC721 (@openzeppelin/contracts/token/ERC721/ERC721.sol). Design the storage, events, and all function logic yourself:

  • Minting requires a small ETH payment (0.001 ETH by default). Reject underpayment; refund any overpayment back to the caller.
  • Store a custom name and a mint timestamp for each token, on-chain. Decide yourself how to structure this data.
  • Track which token IDs each address has minted. The frontend gallery reads this — figure out a storage structure that supports it.
  • The owner can update the mint price and withdraw accumulated ETH from the contract.
  • Emit events to record when a token is minted and when the mint price changes. Decide what data each event should include.
  • Your contract must expose these exact function signatures (the frontend calls them by name):
    • mint(string name) payable
    • setMintPrice(uint256 newPrice)
    • withdraw()
    • getOwnedTokens(address owner) view returns (uint256[])
    • getTokenData(uint256 tokenId) view returns (string name, address tokenOwner, uint256 mintedAt)
    • nextTokenId() view returns (uint256)
    • mintPrice() view returns (uint256)

Implementation guide

ERC-721 inheritance. Inheriting from OpenZeppelin’s ERC721 gives you ownerOf, transferFrom, approve, and all other standard NFT functions for free. The constructor passes the collection name and ticker symbol to the parent.

Overpayment refund. If the user sends more than mintPrice, the excess is returned. This is better UX than reverting — a user who accidentally sends 0.01 ETH instead of 0.001 ETH still gets their NFT and gets 0.009 ETH back.

The _owned mapping. OpenZeppelin’s ERC-721 only tracks the count of tokens per address via balanceOf, not the individual token IDs. To display a gallery in the frontend, we maintain a separate _owned mapping. Note the limitation: this does not update if a token is transferred to another wallet after minting — a good extension exercise.

Withdraw pattern. ETH received by the contract accumulates in its balance until the owner explicitly calls withdraw(). This pull over push approach is safer than the contract trying to push ETH somewhere automatically on every mint.

Option C is a trustless crowdfunding contract — a stripped-down on-chain analogue of Kickstarter. Donors send ETH toward a goal; if the goal is met before the deadline the owner can withdraw, otherwise every donor can claim a full refund. This conditional-release-with-refund pattern appears in token sales, grant programmes, and community treasuries.

The contract is also a direct illustration of the most important security principle in Solidity: specifying precisely who can move funds and under exactly what conditions.

Your contract: Fundraiser.sol

Create Fundraiser.sol in Remix. No OpenZeppelin imports needed — pure Solidity. Design the storage, events, and all function logic yourself:

  • Deploy with a title, description, funding goal (in wei), and a campaign duration in seconds. Calculate the deadline at deploy time.
  • Accept ETH donations while the campaign is active. Track how much each address has donated.
  • If the goal is met before the deadline: only the owner may withdraw all funds, and only once.
    If the campaign ends without meeting the goal: every donor may claim a full refund of their contribution.
  • Both withdraw and refund must follow Checks-Effects-Interactions: update all state before transferring ETH. This is the most important security rule you will apply today.
  • Emit events to record donations, withdrawals, and refunds. Decide yourself what data each event carries.
  • Your contract must expose these exact signatures (the frontend reads them directly):
    • donate() payable
    • withdraw()
    • refund()
    • getStatus() view returns (bool isActive, bool goalReached, uint256 remaining, uint256 timeLeft)
    • Public state variables readable by the frontend: title, description, goal, deadline, totalRaised, withdrawn, owner, donations(address)

Implementation guide

Checks-Effects-Interactions. Both withdraw and refund follow the most important security pattern in Solidity: state is updated first (withdrawn = true / donations[msg.sender] = 0), then ETH is sent. If the transfer were first, a malicious contract could re-enter the function before the state update — this is the reentrancy attack that drained The DAO in 2016 and cost $60 million. Order: Checks → Effects → Interactions, always.

Constructor parameters. The constructor takes _goalInWei directly, not in ETH. For Remix, a goal of 0.01 ETH is 10000000000000000. This avoids needing multiplication at the deployment step.

To test the refund path without waiting an hour, set _durationSeconds to 60 when deploying. After 60 seconds, refund() becomes callable if the goal was not reached.
