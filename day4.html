Day 4

Data Structures and Modifiers

Day 3 covered the mechanics of a Solidity contract — how to declare variables, write functions, and validate input with require(). A contract that stores a counter or a name is easy to follow. But real contracts maintain lists of participants, link every address to some piece of state, and move through a defined lifecycle. Arrays, structs, mappings, and enums make all of that possible.

Before those, one concept that trips up almost everyone coming from other languages: in Solidity, data doesn’t just have a type — it has a location.

Where data lives

In most languages, memory management is the runtime’s problem. Solidity makes you be explicit, because the cost difference between locations is significant. Reading and writing to on-chain storage is orders of magnitude more expensive than working with temporary memory, and understanding the distinction early shapes how you write every function from here on.

Location Where it lives Lifetime Cost
storage The blockchain Permanent — persists after the function returns Most expensive
memory Temporary RAM Erased when the function returns Cheap
calldata Transaction input Read-only, exists only during the call Cheapest

State variables are always storage — you never write the keyword, the compiler assumes it. Where you do have to be explicit is with reference types (strings, arrays, structs) in function parameters and local variables. For value types (uint, bool, address) the compiler handles location automatically, but reference types require you to say where they should live. 

// This compiles: memory tells the EVM this string is temporary
function greet(string memory _name) public pure returns (string memory) {
    return _name;
}

// This does not compile: Solidity requires a data location for string
function greet(string _name) public pure returns (string) { ... }

The practical rule: use memory for function parameters and local variables you’re working with temporarily. For external functions where you only need to read a parameter — not modify it — use calldata instead; it skips the copy and costs a little less gas. The difference is most noticeable when parameters are large strings or arrays.

Arrays

Solidity has two kinds: dynamic (no fixed length, grows at runtime) and fixed-size (length declared upfront, never changes). The one you’ll use most as a state variable is dynamic. 

contract ArrayExample {
    // Dynamic array: grows and shrinks freely
    uint[] public numbers;

    // Fixed-size array: always exactly 5 elements
    uint[5] public fixedNumbers;

    function addNumber(uint _n) public {
        numbers.push(_n);
    }

    function removeLastNumber() public {
        numbers.pop();
    }

    function getLength() public view returns (uint) {
        return numbers.length;
    }

    function getAt(uint _index) public view returns (uint) {
        return numbers[_index];
    }
}

Dynamic arrays stored as state variables support push() to append an element and pop() to remove from the end. There’s no built-in remove-from-middle operation — the Task 3 lab shows the standard pattern for that.

One important safety behaviour: accessing an index that doesn’t exist doesn’t return undefined or zero — it reverts the transaction. numbers[10] on a 4-element array will fail. Any function that accepts a user-supplied index should validate it before using it.

A note on memory arrays: inside a function body, you can declare a fixed-size memory array like uint[] memory arr = new uint[](5), but push() and pop() are not available on it. Those operations exist only on storage arrays.

Structs

A struct groups related fields into a named type. Once defined, you use it the same way you’d use uint or address — as a state variable, as the element type of an array, or as a function parameter. 

contract StudentRegistry {
    struct Student {
        string name;
        uint age;
        bool isEnrolled;
    }

    Student[] public students;

    function addStudent(string memory _name, uint _age) public {
        students.push(Student({
            name: _name,
            age: _age,
            isEnrolled: true
        }));
    }

    function getStudent(uint _index) public view returns (string memory, uint, bool) {
        Student memory s = students[_index];
        return (s.name, s.age, s.isEnrolled);
    }
}

The most common pattern is exactly what’s above: define the record shape with a struct, then keep a dynamic array of that struct as a state variable. This gives you an ordered, appendable list where each element has named fields.

When you read a struct from a storage array into a local variable — Student memory s = students[_index] — it copies the data into temporary memory. Any changes to s don’t affect the stored struct. If you want to update a field in storage, assign directly: students[_index].isEnrolled = false.

Mappings

Mappings are the data structure you’ll use most in Solidity. They’re a key-value store: you write a key, you get the associated value. The syntax is mapping(keyType => valueType). 

contract Balances {
    mapping(address => uint) public balances;

    function deposit(uint _amount) public {
        balances[msg.sender] = balances[msg.sender] + _amount;
    }

    function getBalance(address _user) public view returns (uint) {
        return balances[_user];
    }
}

Two things set mappings apart from dictionaries in most other languages.

First, every possible key already has a value. You never check whether a key “exists” in a mapping — you just read it, and if you haven’t written anything there, you get the zero value: 0 for uint, false for bool, address(0) for address. This means balances[anyAddress] is always safe to read, even for an address that has never interacted with the contract.

Second, mappings cannot be iterated. You can’t loop over all keys, you can’t check how many keys have been written, and there’s no .length. The only operation is looking up a specific key. If you need to enumerate — for example, to pay out every address that deposited — you have to maintain a separate array of addresses and push to it every time a new address first writes to the mapping.

Mappings are constant-time for both reads and writes. This is why they’re used everywhere performance matters: token balances, ownership records, voting registries, access control lists.

Enums

An enum defines a finite, named set of states. Under the hood each value is stored as a uint starting from 0, but you write and compare using the names. This prevents a whole class of bugs where an integer argument has the wrong meaning. 

contract ShippingStatus {
    enum Status { Pending, Shipped, Delivered, Cancelled }

    Status public currentStatus;

    function ship() public {
        currentStatus = Status.Shipped;
    }

    function isDelivered() public view returns (bool) {
        return currentStatus == Status.Delivered;
    }
}

Use enums whenever something in your contract has a discrete lifecycle: an order moving through Pending → Shipped → Delivered → Cancelled, an auction moving through Accepting → Active → Closed, a vote session that hasn’t started, is open, or has ended. The compiler will flag invalid assignments — you can’t accidentally set status to 99.

Two patterns that appear together in nearly every production contract. Events give your contract a way to write output that external code can read — not a state change, but a permanent log attached to the transaction. Modifiers let you write an access rule once and attach it to as many functions as need it, rather than repeating the same require() everywhere.

Events

When a function emits an event, a log entry is written into the transaction receipt. That log is stored by every Ethereum node and is permanently associated with the transaction — but it sits outside the contract’s storage, and you cannot read it from within Solidity code. Events are strictly write-only from the contract’s perspective. They exist for the outside world. 

contract EventExample {
    event Transfer(address indexed from, address indexed to, uint amount);

    function transfer(address _to, uint _amount) public {
        // transfer logic here

        emit Transfer(msg.sender, _to, _amount);
    }
}

Two reasons to use events instead of storing history in state variables. First, gas. Writing a new value to a state variable costs around 20,000 gas. Emitting an event with the same information costs a fraction of that. For any contract that needs a full history of every action — every deposit, every vote, every transfer — events are the right tool.

Second, indexability. The indexed keyword on an event parameter means that block explorers and frontends can filter by that field efficiently. Every ERC-20 token’s Transfer event indexes both from and to, which is why Etherscan can show you the complete token transfer history for any address. You can mark up to 3 parameters as indexed per event. Non-indexed parameters are still stored in the log — they just can’t be filtered by.

After deploying a contract in Remix and calling a function that emits an event, expand the transaction entry in the console. The Logs section shows the event name and the decoded parameter values. On a verified contract on Etherscan, the same data appears on the Logs tab of every transaction.

Modifiers

A modifier wraps a function with additional logic that runs before the function body executes. If the modifier reverts, the function body never runs. 

contract Owned {
    address public owner;

    constructor() {
        owner = msg.sender;
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "Not the owner");
        _;
    }

    function sensitiveAction() public onlyOwner {
        // this line only runs if msg.sender == owner
    }

    function anotherRestrictedFunction() public onlyOwner {
        // same check, one word instead of one line
    }
}

The _; is a placeholder that marks where the function’s own body executes. Everything written before _; in the modifier runs as a precondition. Anything after it (uncommon) runs after the function body returns.

You already wrote require(msg.sender == owner, ...) directly inside functions in Day 3. The modifier version does the same thing — the benefit shows up when you have five functions that all need the same check. One modifier, applied with one word, means the check lives in one place. If you later want to change the ownership logic — for example, to allow a multisig wallet instead of a single address — you update the modifier and every function gets the change automatically.

Multiple modifiers can be applied to a single function. They run left to right: 

modifier whenNotPaused() {
    require(!paused, "Contract is paused");
    _;
}

// onlyOwner runs first, then whenNotPaused, then the function body
function withdraw() public onlyOwner whenNotPaused {
    // ...
}

The TodoList is a complete contract. It manages a real list of tasks with create, complete, and delete operations, ownership-based access control, and event logs on every state change. Every line uses something from Day 3 or Day 4. Write it yourself before reading the full code.

The TodoList contract

Walk through what each part does before looking at the full code.

The Task struct holds three fields: text, a completed flag, and createdAt — the block timestamp when the task was added. The timestamp isn’t needed for this contract to function correctly, but recording it is a pattern worth establishing early. Any feature involving deadlines, expiry, or time-based logic depends on having stored when something was created.

The delete operation uses the swap-and-pop pattern: copy the last element into the slot being deleted, then pop the last element. The array stays compact and the operation costs the same regardless of where in the array the deletion happens. The tradeoff: task order changes when a deletion occurs — whatever was last moves into the deleted slot. For a task list that’s acceptable; for a contract where order matters, you’d need a different approach. 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.10;

contract TodoList {
    address public owner;

    struct Task {
        string text;
        bool completed;
        uint createdAt;
    }

    Task[] public tasks;

    event TaskAdded(uint indexed taskId, string text);
    event TaskCompleted(uint indexed taskId);

    constructor() {
        owner = msg.sender;
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "Only owner can do this");
        _;
    }

    function addTask(string memory _text) public {
        tasks.push(Task({
            text: _text,
            completed: false,
            createdAt: block.timestamp
        }));
        emit TaskAdded(tasks.length - 1, _text);
    }

    function completeTask(uint _index) public {
        require(_index < tasks.length, "Task does not exist");
        require(!tasks[_index].completed, "Already completed");
        tasks[_index].completed = true;
        emit TaskCompleted(_index);
    }

    function deleteTask(uint _index) public onlyOwner {
        require(_index < tasks.length, "Task does not exist");
        tasks[_index] = tasks[tasks.length - 1];
        tasks.pop();
    }

    function getTaskCount() public view returns (uint) {
        return tasks.length;
    }
}

Testing in Remix

Deploy with Remix VM (Shanghai). Then run through these steps in order — the last three test the failure paths, which matter as much as the success cases.

  1. Call addTask three times with "Learn Solidity", "Deploy a contract", and "Build a dApp".
  2. Call getTaskCount — it should return 3.
  3. Call completeTask with index 0. The transaction succeeds. Click the tasks button with input 0 to confirm completed is now true.
  4. Call completeTask with index 0 again. This time it should revert with "Already completed". Confirm the red circle in the Remix console.
  5. Call deleteTask with index 1. This works because you’re the deployer. Call getTaskCount — it should return 2. The last task moved into slot 1.
  6. Switch to a different account in the Accounts dropdown. Call deleteTask again. It should revert with "Only owner can do this", confirming that the onlyOwner modifier is enforced.

The SimpleVote challenge

Build this from scratch before looking at the solution. Each function has one or two things to figure out on your own. 

Contract: SimpleVote

State:
  candidates  — dynamic string array
  votes       — mapping from candidate index to vote count
  hasVoted    — mapping from address to bool (prevents double voting)
  owner       — address, set at deployment

Functions:
  addCandidate(string) — appends a candidate name (onlyOwner)
  vote(uint)           — casts one vote for a candidate index
  getVotes(uint)       — returns the vote count for a candidate
  getWinner()          — returns the name of the leading candidate

Three things to work out before looking at the solution:

  • vote() needs to prevent the same address from voting twice. You have a mapping from address to bool. Check it before recording the vote, then set it to true after.
  • vote() also needs to reject an invalid candidate index. The candidates array has a .length — use it.
  • getWinner() is the first function you’ve written that needs a loop. You need to iterate over candidates, check votes[i] against a running maximum, and track the index of whoever is leading. In case of a tie, return whichever candidate reached that count first.

When you’re ready to check your work:

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.10;

contract SimpleVote {
    address public owner;
    string[] public candidates;
    mapping(uint => uint) public votes;
    mapping(address => bool) public hasVoted;

    constructor() {
        owner = msg.sender;
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "Not the owner");
        _;
    }

    function addCandidate(string memory _name) public onlyOwner {
        candidates.push(_name);
    }

    function vote(uint _index) public {
        require(!hasVoted[msg.sender], "Already voted");
        require(_index < candidates.length, "Invalid candidate");
        votes[_index] = votes[_index] + 1;
        hasVoted[msg.sender] = true;
    }

    function getVotes(uint _index) public view returns (uint) {
        return votes[_index];
    }

    function getWinner() public view returns (string memory) {
        require(candidates.length > 0, "No candidates");
        uint maxVotes = 0;
        uint winnerIndex = 0;
        for (uint i = 0; i < candidates.length; i++) {
            if (votes[i] > maxVotes) {
                maxVotes = votes[i];
                winnerIndex = i;
            }
        }
        return candidates[winnerIndex];
    }
}

Test the full flow in Remix: add three candidates (only the deployer can), switch to a second account and vote, switch to a third and vote for a different candidate, then call getWinner(). Then try voting a second time from the same account — it should revert. Try calling addCandidate from a non-owner account — that should revert too.
