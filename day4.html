Day 4

Data Structures and Modifiers

Day 3 covered the basics of a Solidity contract — declaring variables, writing functions, and validating input with require(). That’s enough to store a number or a name. But real-world contracts do much more: they track lists of participants, tie every wallet address to its own balance or vote, and progress through defined stages like “Pending” or “Completed”. Arrays, structs, mappings, and enums are the four building blocks that make all of that possible. By the end of this task you will have used all of them.

Before diving in, there is one concept that catches almost every newcomer by surprise: in Solidity, data doesn’t just have a type — it also has a location. That location directly affects both the cost of your contract and whether changes you make to a variable are actually saved.

Where data lives

In most languages the runtime handles memory for you and you never have to think about it. Solidity makes you be explicit, and it matters because the three locations have very different costs. Storage is permanent — everything written there lives on the blockchain forever, and that permanence is expensive to write. Memory is temporary scratch space that disappears when the function returns; cheap, but gone. Calldata is the read-only input that arrives with the transaction call itself — you can’t modify it, and it’s the cheapest of the three. The table below lays this out, but the thing to really internalise is that getting the location wrong doesn’t just affect correctness — it can make a contract noticeably more expensive for everyone who uses it.

Location Where it lives Lifetime Cost
storage The blockchain Permanent — persists after the function returns Most expensive
memory Temporary RAM Erased when the function returns Cheap
calldata Transaction input Read-only, exists only during the call Cheapest

State variables (declared at the top of your contract, outside any function) are always storage — you never write the keyword because the compiler already knows. Where you do have to be explicit is inside functions, when working with reference types: strings, arrays, and structs. Simple value types like uint, bool, and address are handled automatically, but anything that can have a variable size requires you to tell the compiler whether it should live in memory or calldata. 

// This compiles: memory tells the EVM this string is temporary
function greet(string memory _name) public pure returns (string memory) {
    return _name;
}

// This does not compile: Solidity requires a data location for string
function greet(string _name) public pure returns (string) { ... }

In practice: use memory for function parameters and local variables you need to work with or modify. If a parameter only needs to be read — not changed — use calldata instead. It skips copying the value into memory, which saves a little gas. The difference is negligible for a single uint, but it adds up when parameters are long strings or large arrays.

Arrays

An array is an ordered list of values, all of the same type. If you need to keep track of multiple numbers, addresses, or structs, an array is the go-to. Solidity has two flavours: a dynamic array has no fixed length and can grow or shrink at runtime (the one you will use most), while a fixed-size array has its length set at compile time and can never change. 

contract ArrayExample {
    // Dynamic array: grows and shrinks freely
    uint[] public numbers;

    // Fixed-size array: always exactly 5 elements
    uint[5] public fixedNumbers;

    function addNumber(uint _n) public {
        numbers.push(_n);
    }

    function removeLastNumber() public {
        numbers.pop();
    }

    function getLength() public view returns (uint) {
        return numbers.length;
    }

    function getAt(uint _index) public view returns (uint) {
        return numbers[_index];
    }
}

Dynamic storage arrays support two built-in operations: push() adds a new element to the end, and pop() removes the last one. There is no built-in way to remove an element from the middle of the array — Task 3 shows the standard pattern (swap-and-pop) for doing that efficiently.

One important safety detail: if you try to access an index that doesn’t exist, Solidity does not return undefined or silently give you a zero like some other languages would. It reverts the entire transaction. Calling numbers[10] on a 4-element array will fail and roll back. This means any function that takes a user-supplied index should always check that the index is within bounds before using it.

One thing to be aware of with memory arrays: you can create a temporary fixed-size array inside a function with uint[] memory arr = new uint[](5), but push() and pop() are not available on it. Those two operations only work on arrays that live in storage.

Structs

A struct lets you group several related pieces of data under one name. Think of it as designing your own custom data type — like a row in a spreadsheet where each column has a label and a type. Once you define a struct, you can use it exactly like any built-in type: store it in a state variable, make it the element type of an array, or pass it as a function parameter. 

contract StudentRegistry {
    struct Student {
        string name;
        uint age;
        bool isEnrolled;
    }

    Student[] public students;

    function addStudent(string memory _name, uint _age) public {
        students.push(Student({
            name: _name,
            age: _age,
            isEnrolled: true
        }));
    }

    function getStudent(uint _index) public view returns (string memory, uint, bool) {
        Student memory s = students[_index];
        return (s.name, s.age, s.isEnrolled);
    }
}

The most common pattern is exactly what you see above: define the shape of your record with a struct, then maintain a dynamic array of those structs as a state variable. This gives you a growing, ordered list where each entry has named, typed fields — much more readable than juggling four separate arrays that have to stay in sync by index.

There is one important behaviour to understand when reading a struct. Writing Student memory s = students[_index] makes a copy of that struct into temporary memory. Any changes you make to s only affect the copy — they do not update what is stored on-chain. If your intention is to actually change a stored value, you must write to the array directly: students[_index].isEnrolled = false. This is a very common source of bugs for newcomers, so it is worth remembering.

Mappings

Mappings are the data structure you will reach for most often in Solidity. A mapping works like a lookup table or a phonebook: you give it a key and it instantly gives back the associated value. The key is typically an address — the caller’s wallet — and the value is whatever you want to associate with that address: a token balance, a vote, a registration status. The syntax is mapping(keyType => valueType). 

contract Balances {
    mapping(address => uint) public balances;

    function deposit(uint _amount) public {
        balances[msg.sender] = balances[msg.sender] + _amount;
    }

    function getBalance(address _user) public view returns (uint) {
        return balances[_user];
    }
}

Mappings behave differently from dictionaries in most other languages in two ways worth knowing about. First, there’s no such thing as a missing key. In Python or JavaScript you check whether a key exists before reading it. In Solidity every key you can imagine is already present in the mapping — it just holds the zero value until you write something: 0 for uint, false for bool, address(0) for address. Think of a school register where every student ID already has an entry defaulting to zero — you don’t add students, you just update their scores. So balances[anyAddress] is always safe to read, even if that address has never touched your contract.

Second, mappings can’t be iterated. You can’t loop over all the keys, check how many have been written, or get a .length. The only operation is a key lookup. That limitation is intentional — it keeps every read and write instant and gas-predictable no matter how large the mapping grows. If you do need to enumerate — say, to pay out every depositor — you maintain a separate address array alongside the mapping and push to it the first time each address writes in.

Enums

An enum lets you define a fixed, named set of possible states for something. Instead of using raw numbers like 0, 1, 2 to represent stages in a process (which is both hard to read and easy to get wrong), you give each state a meaningful name. Under the hood Solidity stores each value as a uint starting from 0, but you write and compare using the names. This eliminates an entire category of bug where someone passes the integer 5 to a function that only knows about three valid states — the compiler simply won’t allow it. 

contract ShippingStatus {
    enum Status { Pending, Shipped, Delivered, Cancelled }

    Status public currentStatus;

    function ship() public {
        currentStatus = Status.Shipped;
    }

    function isDelivered() public view returns (bool) {
        return currentStatus == Status.Delivered;
    }
}

Use enums wherever something in your contract has a clear lifecycle with a small number of possible stages — an order moving through Pending → Shipped → Delivered → Cancelled, an auction going from Accepting → Active → Closed, a vote session that is either Inactive, Open, or Finalized. The compiler enforces it: you cannot write currentStatus = 99 because 99 simply isn’t a member of your enum. Your intent is readable in the code, and invalid states are caught before the contract ever deploys.

Two patterns appear together in nearly every production contract. Events give your contract a way to broadcast that something happened — not by changing state, but by writing a permanent log entry that the outside world can read. Modifiers let you write an access rule once and attach it to as many functions as need it, rather than copy-pasting the same require() everywhere. Neither is complicated, but both will immediately make your contracts cleaner and cheaper to run.

Events

When a function emits an event, Ethereum writes a log entry into the transaction receipt. Think of it like a receipt printer attached to your contract: every time something important happens, it prints a permanent record. That record is stored by every Ethereum node and is attached to the transaction forever — but here is the key detail: the contract itself cannot read its own event logs. Events are strictly a one-way broadcast to the outside world. Wallets, block explorers like Etherscan, and your frontend application can all read and filter these logs; your Solidity code cannot. 

contract EventExample {
    event Transfer(address indexed from, address indexed to, uint amount);

    function transfer(address _to, uint _amount) public {
        // transfer logic here

        emit Transfer(msg.sender, _to, _amount);
    }
}

The reason to prefer events over storing a history in state variables is mostly cost. Writing a new value to storage costs roughly 20,000 gas; emitting an event carrying the same information is a fraction of that. A contract that stored every deposit, every vote, and every transfer as state would become expensive to use. Events give you the same permanent record without the overhead.

The indexed keyword is what makes those logs useful to the outside world. It tells Ethereum to index that parameter so that block explorers and frontends can filter by it efficiently. Every ERC-20 token’s Transfer event indexes both from and to — which is why Etherscan can show you the full transfer history for any address. You can mark up to three parameters as indexed per event. The rest are still stored in the log, they just can’t be used as a filter.

After deploying a contract in Remix and calling a function that emits an event, expand the transaction entry in the console. The Logs section shows the event name alongside the decoded parameter values. On a verified contract on Etherscan, the same data appears on the transaction’s Logs tab — this is what you are looking at when you inspect a real-world contract.

Modifiers

A modifier is a reusable wrapper for a function. It runs additional logic — typically a permission check — before the function body executes. If the check fails, the transaction reverts and the function body never runs. Think of it as a security checkpoint that sits at the entrance to a function: anyone who doesn’t meet the requirement is turned away before they even get inside. 

contract Owned {
    address public owner;

    constructor() {
        owner = msg.sender;
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "Not the owner");
        _;
    }

    function sensitiveAction() public onlyOwner {
        // this line only runs if msg.sender == owner
    }

    function anotherRestrictedFunction() public onlyOwner {
        // same check, one word instead of one line
    }
}

The _; is a placeholder that marks exactly where the function’s own body should execute. Everything written before _; in the modifier runs as a precondition check. Writing logic after _; is possible (it runs after the function body returns) but uncommon in practice.

In Day 3 you wrote require(msg.sender == owner, ...) directly inside individual functions. That works, but as soon as you have three, five, or ten functions that all need the same check, you have the same logic duplicated in multiple places. With a modifier, the check lives in exactly one place. If you later need to change the ownership logic — say, to support a multisig wallet instead of a single address — you update the modifier once and every function that uses it automatically gets the new behaviour. No hunting through the file for every copy.

A single function can use multiple modifiers at once. They run left to right in the order you write them: 

modifier whenNotPaused() {
    require(!paused, "Contract is paused");
    _;
}

// onlyOwner runs first, then whenNotPaused, then the function body
function withdraw() public onlyOwner whenNotPaused {
    // ...
}

The TodoList is the first contract in this course that does something genuinely useful. It manages a real list of tasks with create, mark-complete, and delete operations, owner-only access control, and event logs on every state change. Every line draws on something from Day 3 or Day 4. Try to write it yourself first — use the feature list below as your spec. Looking at the solution before attempting it yourself will make the learning stick much less.

The TodoList contract

Walk through what each part does before looking at the full code.

The Task struct holds three fields: text (what the task says), a completed flag (has it been done?), and createdAt — the blockchain’s timestamp at the moment the task was added. The timestamp is not strictly required for the contract to function, but recording it is a habit worth building from day one: any feature involving deadlines, expiry windows, or time-based logic needs to know when something was created.

The delete operation uses a pattern called swap-and-pop. Instead of leaving a gap or shifting every element left (which would cost gas proportional to the array size), it copies the last element in the array into the slot being deleted, then pops the last element off. The array stays compact and the operation costs the same regardless of where in the array the deletion happens. There is one tradeoff: the order of your tasks will change when a deletion occurs, because whatever was at the end moves to fill the gap. For a todo list that is perfectly acceptable. For a contract where insertion order must be preserved, you would need a different approach. 

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.10;

contract TodoList {
    address public owner;

    struct Task {
        string text;
        bool completed;
        uint createdAt;
    }

    Task[] public tasks;

    event TaskAdded(uint indexed taskId, string text);
    event TaskCompleted(uint indexed taskId);

    constructor() {
        owner = msg.sender;
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "Only owner can do this");
        _;
    }

    function addTask(string memory _text) public {
        tasks.push(Task({
            text: _text,
            completed: false,
            createdAt: block.timestamp
        }));
        emit TaskAdded(tasks.length - 1, _text);
    }

    function completeTask(uint _index) public {
        require(_index < tasks.length, "Task does not exist");
        require(!tasks[_index].completed, "Already completed");
        tasks[_index].completed = true;
        emit TaskCompleted(_index);
    }

    function deleteTask(uint _index) public onlyOwner {
        require(_index < tasks.length, "Task does not exist");
        tasks[_index] = tasks[tasks.length - 1];
        tasks.pop();
    }

    function getTaskCount() public view returns (uint) {
        return tasks.length;
    }
}

Testing in Remix

Deploy with Remix VM (Shanghai). Then run through these steps in order — the last three test the failure paths, which matter as much as the success cases.

  1. Call addTask three times with "Learn Solidity", "Deploy a contract", and "Build a dApp".
  2. Call getTaskCount — it should return 3.
  3. Call completeTask with index 0. The transaction succeeds. Click the tasks button with input 0 to confirm completed is now true.
  4. Call completeTask with index 0 again. This time it should revert with "Already completed". Confirm the red circle in the Remix console.
  5. Call deleteTask with index 1. This works because you’re the deployer. Call getTaskCount — it should return 2. The last task moved into slot 1.
  6. Switch to a different account in the Accounts dropdown. Call deleteTask again. It should revert with "Only owner can do this", confirming that the onlyOwner modifier is enforced.

The SimpleVote challenge

Build this from scratch before looking at the solution. The spec is written as a description on purpose — converting it into working Solidity is the exercise. 

Contract: SimpleVote

State:
  candidates  — dynamic string array
  votes       — mapping from candidate index to vote count
  hasVoted    — mapping from address to bool (prevents double voting)
  owner       — address, set at deployment

Functions:
  addCandidate(string) — appends a candidate name (onlyOwner)
  vote(uint)           — casts one vote for a candidate index
  getVotes(uint)       — returns the vote count for a candidate
  getWinner()          — returns the name of the leading candidate

Three things to work out before looking at the solution:

  • vote() needs to stop the same address from voting twice. You have a mapping(address => bool) called hasVoted — check it before recording the vote, then set it to true so any repeat attempt from that address gets rejected.
  • vote() also needs to reject an index that doesn’t correspond to any real candidate. The candidates array has a .length — use it.
  • getWinner() is the first function here that needs a loop. Iterate over all candidates, track the running maximum of votes[i], and note the index of whoever is leading. On a tie, the candidate who got there first (lower index) wins.

When you’re ready to check your work:

// SPDX-License-Identifier: MIT
pragma solidity ^0.8.10;

contract SimpleVote {
    address public owner;
    string[] public candidates;
    mapping(uint => uint) public votes;
    mapping(address => bool) public hasVoted;

    constructor() {
        owner = msg.sender;
    }

    modifier onlyOwner() {
        require(msg.sender == owner, "Not the owner");
        _;
    }

    function addCandidate(string memory _name) public onlyOwner {
        candidates.push(_name);
    }

    function vote(uint _index) public {
        require(!hasVoted[msg.sender], "Already voted");
        require(_index < candidates.length, "Invalid candidate");
        votes[_index] = votes[_index] + 1;
        hasVoted[msg.sender] = true;
    }

    function getVotes(uint _index) public view returns (uint) {
        return votes[_index];
    }

    function getWinner() public view returns (string memory) {
        require(candidates.length > 0, "No candidates");
        uint maxVotes = 0;
        uint winnerIndex = 0;
        for (uint i = 0; i < candidates.length; i++) {
            if (votes[i] > maxVotes) {
                maxVotes = votes[i];
                winnerIndex = i;
            }
        }
        return candidates[winnerIndex];
    }
}

Test the full flow in Remix: add three candidates (only the deployer can, try it from a different account to confirm the revert), switch to a second account and vote for one candidate, switch to a third account and vote for a different candidate, then call getWinner() to confirm the right name is returned. Finally, vote a second time from the same account — it should revert with “Already voted”. Cover both success and failure paths: the failure cases are just as important as the ones that are supposed to work.
